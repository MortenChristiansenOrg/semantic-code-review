# v0.15.0-rc.3 — 2026-11-24

## Overview

This is the third prerelease of 0.15.0. It is less tested than a normal release and is published so that it can be tried before everyone gets it. Plain `/semantic-flow update` does not install it; `/semantic-flow update -p` does. These notes describe what changed since 0.15.0-rc.2. The notes of [0.15.0-rc.1](https://github.com/MortenChristiansenOrg/semantic-code-review/releases/tag/v0.15.0-rc.1) and [0.15.0-rc.2](https://github.com/MortenChristiansenOrg/semantic-code-review/releases/tag/v0.15.0-rc.2) describe what changed before.

This prerelease fixes stages that could not be organized again after a restack or sync.

Versions beginning with zero remain experimental: any release, including a patch, may contain breaking changes.

## Breaking changes

None since 0.15.0-rc.2.

## Bug fixes

- **Organizing a stage again after a restack or sync.** A restack or sync records each stage's new changes even when the stage's nodes no longer fit them, for example when a file was committed to a finished stage before restacking, or when the target already makes one of a stage's changes. `stage plan --finalized` and `stage organize --finalized` then refused with the same error that `validate` reported, so the stage could only be fixed by resetting the implementation by hand. Now both commands work on such a stage. When several stages need it, organize them one at a time: organizing one stage no longer requires the others to fit. The validation error names the commands that fix the stage ([#275](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/275)).

## Updating

From 0.15.0-rc.2, run `/semantic-flow update -p` between feedback rounds, then run `/semantic-flow review` again. Implementations in progress continue across the update.

From 0.15.0-rc.1, read the [0.15.0-rc.2 notes](https://github.com/MortenChristiansenOrg/semantic-code-review/releases/tag/v0.15.0-rc.2) first: let the listening agent finish its round and stop it before you update, because this version requires the round claims that 0.15.0-rc.2 introduced.

From 0.14.0 or older, first read the [0.15.0-rc.1 notes](https://github.com/MortenChristiansenOrg/semantic-code-review/releases/tag/v0.15.0-rc.1) and the [0.15.0-rc.2 notes](https://github.com/MortenChristiansenOrg/semantic-code-review/releases/tag/v0.15.0-rc.2): their breaking changes apply, and implementations in progress cannot continue across the update. Then follow the steps under Updating in the 0.15.0-rc.1 notes, with `semantic-flow-0.15.0-rc.3.zip` and `semantic-flow-0.15.0-rc.3.zip.sha256` from this release. Their updater cannot install a prerelease, so the skill folder is replaced once by hand. [Installing and updating](https://github.com/MortenChristiansenOrg/semantic-code-review/blob/master/docs/releases.md#installing-and-updating) describes each step.

`/semantic-flow update -p` (or `--prerelease`) installs the newest version including prereleases, which are less tested than normal releases. The option applies to that run only. Plain `/semantic-flow update` stays on normal releases: on a prerelease it changes nothing until a normal release of the same version or newer exists, and then installs it.

Viewer pages that are open during an update need a fresh link afterwards: run `/semantic-flow review` again.

Node.js 22 or newer and Git are required for the CLI and viewer. Windows, macOS and Linux are supported.

The implementation and feedback formats remain experimental `0.1` and did not change since 0.15.0-rc.2.

## Known issues

- **Attributes can still change a stage's inventory and diffs.** Attributes in the repository's `info/attributes` file, and with Git older than 2.41 also `.gitattributes` in the checkout, can still change what a stage's inventory lists and how its files are compared. They now apply the same way everywhere. This will not be fixed ([#236](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/236)).
- **A commit at the moment of a takeover.** If a second agent takes a round over between the first agent's last check and its `git commit`, that commit can still land on a stage branch. The restack that would record it is refused, and the new agent takes it over as leftover work.
