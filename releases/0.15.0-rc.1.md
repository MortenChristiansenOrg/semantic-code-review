# v0.15.0-rc.1 — 2026-11-22

## Overview

This is a prerelease of 0.15.0. It is less tested than a normal release and is published so that it can be tried before everyone gets it. Plain `/semantic-flow update` does not install it. From a version that knows prereleases, `/semantic-flow update -p` does; from 0.14.0 or older, install it once by hand as described under Updating.

0.15.0 is a large release:

- An implementation's data now lives in Git instead of in a folder in your worktree.
- Every finished stage is exactly one commit, and the CLI handles restack conflicts.
- Archiving no longer adds a commit to your target branch.
- `/semantic-flow review` keeps the agent listening for feedback; there is no separate mode for it.
- Other web pages can no longer use the viewer's review data.

Much of the CLI and the viewer was also rebuilt internally. Please report anything that worked in 0.14.0 and no longer does, with `/semantic-flow report`.

Versions beginning with zero remain experimental: any release, including a patch, may contain breaking changes.

## Breaking changes

- **Node.js 22 or newer is required.** Node.js 20 is no longer supported. Install Node.js 22 or newer before updating.
- **The updater of 0.14.0 and older cannot install this version.** It ignores prereleases. It will also reject the normal 0.15.0, because that release ships only `semantic-flow.mjs` ("Release is missing scripts/semantic-implementation.mjs"). Replace the skill folder once by hand, as described under Updating.
- **Implementations in progress cannot continue across the update.** Archive finished implementations, and finish or discard the others, with the old version first. Their reviews do not carry over either: an implementation started with this version gets a new review, without the old threads, drafts, notes and approvals. Three things changed:
  - The active artifact is stored in Git, under `refs/semantic-review/active/`, instead of in a `.semantic-review/` folder. This version reports a leftover `.semantic-review/` folder instead of reading it; remove the folder once its work is done.
  - Stage data such as a stage's branch, base and file list is derived from Git instead of stored.
  - Stage branches are named by stage ID, as in `my-prefix/stages/checkout-totals`, instead of by position.
- **One executable.** The skill ships only `scripts/semantic-flow.mjs`. The programs `semantic-implementation.mjs`, `review-feedback.mjs` and `semantic-view.mjs` are gone. Their commands are now the groups `semantic-flow.mjs implementation`, `semantic-flow.mjs feedback` and `semantic-flow.mjs viewer serve`. The `repair` command is gone, with no replacement: an artifact change is now one Git snapshot instead of several file writes. Scripts of your own that called the old programs, or that read files in `.semantic-review/`, need changing. Use `implementation export` to read the artifact's data, and `inspect --json` to find the active implementations, their worktrees and their feedback folders.
- **`/semantic-flow review` always listens.** On an active local implementation it opens the viewer and keeps the agent listening for feedback until the review ends. The `-i` and `--interactive` options and the separate "interactive review" are gone.
  - A review that is marked complete has no listener. Choose **Reopen review** in Saved reviews, then run `/semantic-flow review` again.
  - `/semantic-flow feedback` remains for handling waiting feedback once, without listening.
  - Reviewing someone else's branch with `review --branch` still has no listener.
  - Running the CLI's `review` command yourself only opens the viewer.
- **A finalized stage is one commit.** `stage finish`, `stage organize --finalized` and `restack` fold a stage's commits into one commit. Its message comes from the stage title and summary. The other authors of the folded commits become co-authors, and existing co-authors are kept. Validation rejects a finalized stage of several commits.
- **The CLI handles restack conflicts.** Stages are replayed by cherry-pick. A conflict is resolved in the scratch worktree that the command reports and completed with `restack --continue`, or discarded with `restack --abort`, instead of the earlier manual recipe. A stage whose changes the target branch already contains stays as a marked empty stage, which stack preparation skips.
- **Archiving no longer touches the target branch.** `archive` stores the implementation under a private Git ref, `refs/semantic-review/archive/` followed by the implementation ID.
  - It no longer commits `.semantic-review-history/` to the target branch, and it has no `--destination`.
  - It needs neither the target branch checked out nor the work to have landed. It records where the work landed: detected when the target branch contains the final stage commit, supplied with `--landed`, or unknown.
  - On request it shares an archive as a tag, `semantic-review-archive/` followed by the implementation ID.
  - Archives already committed under `.semantic-review-history/` stay as they are.
- **Stage inventories no longer depend on your Git configuration.** A stage's inventory is its list of changed files. It now lists submodule updates and inexact renames even where `diff.ignoreSubmodules`, a submodule `ignore` setting, a low `diff.renameLimit` or attributes that marked a file binary hid them. It also ignores replacement refs. The nodes of such a stage may need to assign those paths. Known issues lists what can still differ.
- **The viewer needs a fresh link.** Other web pages can no longer read or change a review through the viewer. The viewer's own page gets access through a code in the link that `review` opens or prints.
  - A link works once and for ten minutes. A new tab, a bookmark, or a tab left open while the viewer restarted shows "This review page needs a fresh link." Run `/semantic-flow review` again to get one.
  - Markdown previews no longer load images from local addresses such as `localhost` and `127.0.0.1`. Images in the repository still load.
  - The address `/implementation-data.js` is gone, and a script that stops the viewer through its shutdown address now needs the viewer's key. Installing and updating, linked under Updating, describes it.
- **Reserved branch names.** `init --branch-prefix` refuses a prefix whose first part is `semantic-review`, `semantic-review-archive` or `refs`. `prepare-branch --branch` refuses a name that starts with `semantic-review/`, `semantic-review-archive/` or `refs/`.
- **Reviews of missing repositories are removed.** When saved reviews are listed or a review is started, each local review whose repository's Git directory is missing is noted. If the directory is still missing 30 days later, the review is removed without asking. **Retry deletion** is gone: files left behind by a deletion are removed by a later cleanup.

## Improvements

- **Implementation data is safe in Git.** The active artifact is a private Git ref that every worktree of the repository shares. `git clean` can no longer remove it. A review now belongs to the implementation instead of to a checkout path, so moving or recreating a worktree keeps your threads, notes and approvals.
- **Send feedback automatically.** While an agent is listening, tick **Send automatically** next to **Prepare feedback** to send each feedback note and reply as soon as you save it. Earlier drafts wait for **Prepare feedback**, and personal notes stay local. The viewer remembers the choice.
- **Line threads follow their line.** After a correction or a restack, a thread on a line is shown on that same line, also when its line number moved, as long as the line is unchanged in the same file and on the same side of the diff. Otherwise the thread is shown at file level with its original line and a notice that stays after the agent replies. When the file left the diff, the thread is in the notes panel.
- **Empty stages are marked and removed.** The viewer labels a stage that no longer changes anything, and `status`, `validate` and stack preparation count and name empty stages the same way.
  - The agent removes an empty stage once no thread on it is open, with the new `implementation stage remove`, and says so in its reply. The only stage of an implementation is kept.
  - The stages above keep their content, approvals and threads. The removed stage's resolved threads stay readable.
  - Removing a stage deletes its branch. A pull request that was based on that branch needs a new base.
  - Preparing a cumulative branch refuses a stack in which every stage is empty.
- **Restacking is more dependable.**
  - Renames and moved directories merge as Git merges them.
  - When `sync` or `feedback` detached your worktree for a restack, `restack --abort` and a completed `restack --continue` switch it back to its stage branch, when that is safe.
  - A changed stage title or summary reaches the stage's commit message at the next restack.
- **An archived implementation ends cleanly in the viewer.** At its next request, an open page shows "Implementation archived", together with approval changes and text that were not saved. The review list shows the review as Archived. The viewer process stops by itself once no page has made a request for ten minutes.
- **Landing can be recorded later.** `implementation archive landing` records where an archived implementation landed. `implementation archive share` creates the tag to push; after that the record no longer changes.
- **Keyboard access.** A tooltip taller than the window scrolls with the arrow keys, Page Up, Page Down, Home and End; this was the known issue of 0.14.0. In the Markdown preview, tooltips on images and other elements that are not links can be reached with Tab.
- **macOS.** The skill's runtime guide now covers macOS. Before, an agent on macOS stopped before making any change.
- **Export.** `implementation export` prints the artifact's data as JSON, or writes it together with its evidence files to a new or empty folder.
- **Prereleases.** A version can be published as a prerelease first. See Updating.

## Bug fixes

- **Unusual file names and IDs.** Feedback on a file whose name contains a line break can be sent. File names and IDs with characters such as quotes work in the viewer. Stages and specifications with IDs such as `constructor` keep their approvals and open state after a reload.
- **Commands run from a Git hook.** Git sets variables such as `GIT_DIR` for hooks and for `git rebase --exec`. The CLI passed them on, so its Git commands could act on another repository than the one it had selected. It now ignores them.
- **Windows.** Replacing review data or artifact files is retried for up to two seconds while another process reads them, instead of failing at once. `update` keeps the new installation when the old one cannot be deleted, and names the leftover folder.
- **Interrupted refresh of a remote review.** A review of someone else's branch whose refresh was interrupted, for example because the viewer was stopped, failed on every request afterwards. It is now rebuilt when it is opened.

## Updating

1. Install Node.js 22 or newer. Node.js 20 is no longer supported.
2. With your current version, archive finished implementations and finish or discard the others. This version cannot continue them, and their reviews do not carry over.
   - 0.14.0 archives an implementation only when the target branch contains its final stage commit. To keep work that it cannot archive, keep a copy of its `.semantic-review/` folder and of the old skill folder.
   - This version reports a leftover `.semantic-review/` folder instead of reading it. Remove that folder once its work is done.
3. Install this version. From 0.14.0 or older, replace the skill folder once by hand. Their updater ignores prereleases, and it also rejects a release that ships only `semantic-flow.mjs`, as the normal 0.15.0 will:
   1. Download `semantic-flow-0.15.0-rc.1.zip` and `semantic-flow-0.15.0-rc.1.zip.sha256` from this release. Use these uploaded files, not GitHub's source code archive. Verify the checksum.
   2. Stop a running viewer and wait for it to exit.
   3. Move the old `semantic-flow` folder out of your harness's skills directory and keep it as a backup.
   4. Put the complete extracted `semantic-flow` folder in its place.
   5. Run the `version` command. Then open a review of a new implementation, or of a remote branch, to check the viewer. Restore the backup if this fails.

[Installing and updating](https://github.com/MortenChristiansenOrg/semantic-code-review/blob/master/docs/releases.md#installing-and-updating) describes each step, including how to verify the checksum and how to stop the viewer.

From this version on, `/semantic-flow update -p` (or `--prerelease`) installs the newest version including prereleases, which are less tested than normal releases. The option applies to that run only. Plain `/semantic-flow update` stays on normal releases: on a prerelease it changes nothing until a normal release of the same version or newer exists, and then installs it. Updaters up to 0.14.0 cannot install a prerelease, which is why the first one is installed by hand.

Viewer pages that are open during an update need a fresh link afterwards: run `/semantic-flow review` again.

Node.js 22 or newer and Git are required for the CLI and viewer. Windows, macOS and Linux are supported. Highlighting the other occurrences of selected text in the viewer needs a current browser.

The implementation and feedback formats remain experimental `0.1` and changed in place. The manifest lists each stage by its ID and head commit, and removed stages under `removedStages`. An archive adds `landing.json`. `docs/artifact-format.md` and `docs/feedback-format.md` describe the formats.

## Known issues

- **Two agents on one review.** Starting `/semantic-flow review` in a second agent while the first is in the middle of a feedback round takes over that round at once. The first agent finds out only when it posts its replies or starts its next wait, so until then both can change the same stages. Start a second agent only when the first has stopped. Tracked in [#250](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/250).
- **Removed lines of a renamed file.** A note on a removed line of a file that the stage renames cannot be sent ([#234](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/234)). An existing thread on such a line moves to file level when the stage's head commit changes ([#235](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/235)).
- **Attributes can still change a stage's inventory.** Attributes in the repository's `info/attributes` file, and with Git older than 2.41 also `.gitattributes` in the checkout, can still change what a stage's inventory lists. Tracked in [#236](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/236).
- **Diffs can differ from the inventory.** With settings such as `diff.ignoreSubmodules`, the viewer's diffs, the reconstruction of a remote review and the CLI's selectors can show other files than the stage inventory lists. Tracked in [#237](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/237).
- **Keyboard focus under the top bar.** Moving focus with Tab can scroll the focused element under the viewer's top bar. Tracked in [#239](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/239).
- **Cleaning unused files.** Cleaning a review's unused files can remove an attachment of a thread whose file is missing. Tracked in [#241](https://github.com/MortenChristiansenOrg/semantic-code-review/issues/241).
